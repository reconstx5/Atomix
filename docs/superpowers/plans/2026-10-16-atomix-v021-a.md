# Atomix Round 23 — Plan A (preparing downloads on the server) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The server can prepare a phone-sized copy of a film, episode, recording or song for an account allowed to download, keep it in a cache, hand it to a device in resumable pieces, and tell a device which of its downloads it may keep.

**Architecture:** Migration 23 adds `users.can_download` and `download_jobs`. `src/downloads/plan.js` decides copy vs convert and builds the ffmpeg arguments (pure). `src/downloads/queue.js` (`DownloadQueue`) runs one job at a time at low priority, yields while a converted video plays (the same `busy()` the background tasks use), reports progress, and keeps the cache within its limits. `src/api/downloads.js` holds the routes. Settings and the admin screens gain a Downloads card, a per-account switch and a Dashboard line.

**Tech Stack:** Node ≥ 22.13, `node:sqlite`, ffmpeg/ffprobe; `node:test`; Playwright devtools.

**Spec:** `docs/superpowers/specs/2026-10-16-atomix-v021-design.md` (section 1, Hard limits, Testing). Plan B (the device side) consumes these routes.

## Global Constraints

- No dependencies; plain ES modules.
- `users.can_download`: admins 1, everyone else 0 on upgrade and for new users (an admin created later also 1).
- Without it: 403 "Downloads aren't switched on for this account. Ask an admin." Server switch off: 403 "Downloads are switched off on this server."
- Connected-server titles: 400 "Downloads aren't available for titles from a connected server yet." Live TV channels and add-on sources are not titles here (only `movie`, `episode`, `track` items).
- Kids profiles: only titles they may watch (`library.canSee`); no other refusal for Kids.
- Qualities `480` (~1 Mb/s), `720` (~2.5 Mb/s, default), `1080` (~5 Mb/s); formats `mp4` (H.264/AAC, `+faststart`), `webm` (VP9/Opus, for a browser without H.264), `audio` (songs: AAC 192 kb/s in MP4, or the original when the browser plays its codec).
- Video audio: 2 channels, AAC 160 kb/s (mp4) / Opus 128 kb/s (webm). Text subtitles served as `.vtt`; picture subtitles not included.
- Cache: `<data>/downloads/` or the admin's folder; files unused 7 days are removed; total kept under `downloadsCacheGb` (default 50), oldest `used_at` first.
- Settings: `downloadsEnabled` true, `downloadsDir` '', `downloadsCacheGb` 50 (1–2000), `downloadQuality` '720', `downloadOfflineDays` 30 (7–90), `downloadDeviceGb` 20 (1–500).
- Provider URLs, file paths and tokens never reach the browser; `/file` answers `private, no-store`.
- Older themes pixel-identical; Kids never see admin settings.

## Review Focus

1. **A Range request that starts in the middle and one past the end** — 206 with the right `Content-Range`, 416 past the end (Task 4 test `the file is served in resumable pieces`).
2. **The same title asked for by two profiles at once** — one job, one ffmpeg, both get its id (Task 3 test `one job per title, quality and format`).
3. **A job whose ffmpeg fails or whose source file vanished** — status `failed` with a sentence, the partial file removed, a later request starts it again (Task 3 test `a failed job says why and can be asked again`).
4. **Switching an account's downloads off while its device holds titles** — `check` returns them all in `remove` (Task 4 test `check removes what may no longer be kept`).
5. **The cache limit reached while a job is preparing** — the oldest ready files go, never a file being fetched in the last minute or the job in progress (Task 3 test `the cache keeps under its size, oldest first`).

### Task 3: The queue and the cache

**Files:**
- Create: `src/downloads/queue.js` (`DownloadQueue`), `src/downloads/rules.js` (`canDownload`, from Task 1)
- Modify: `src/app.js` (`core.downloads = new DownloadQueue({ db, config, settings, busy, hooks })`, started with the app, stopped in `stop`; the `busy` function the background tasks get is shared, and for downloads it is also true while a recording is joining — `core.live?.recordings` exposes `joining() → boolean`), `src/config.js` (`downloadsDir` default `<data>/downloads`)
- Test: `test/downloads-queue.test.js`

**Interfaces:**
- Consumes: Task 2 `planDownload`, `downloadArgs`.
- Produces: `DownloadQueue.request(item, { quality, format }) → { id, status, progress, size }` (an existing job for the same item/quality/format is returned; a `failed` one is reset to `queued`); `.get(id) → job row | null`; `.fileFor(id) → absolute path | null` (only when `ready`; sets `used_at`); `.preparingCount() → number`; `.cleanup(now = Date.now())`; events through `hooks.emit('downloads:ready', { job })`. Job files are `<dir>/<id>-<quality>.<ext>`, written as `.part` and renamed when ffmpeg exits 0.

- [ ] **Step 1: Write failing tests** with real short files (`makeVideo` 4 s, `makeAudio`): `one job per title, quality and format` (two `request`s in the same tick → same id, one ffmpeg spawn counted through an `onSpawn` hook); a job runs to `ready` with `progress` reaching 1 and `size` the file's size, the file playable (`ffprobe` sees H.264 + AAC, height 720 for a 1080 source made with `makeVideo({ size: '1920x1080' })` or the helper's equivalent); `jobs run one at a time` (two titles: the second stays `queued` until the first is `ready`); `it waits while a converted video plays` (`busy()` true → stays `queued`; false → runs); `a failed job says why and can be asked again` (source deleted → `failed`, error "The file is missing on the server — try rescanning the library.", no `.part` left; a new `request` → `queued`); `the cache keeps under its size, oldest first` (limit set tiny: the oldest `used_at` ready file is removed, a file used in the last minute and the running job are not); files unused 7 days removed by `cleanup(now + 8 days)`; a `copy` plan copies (no encoder in the args, same bytes length class).
