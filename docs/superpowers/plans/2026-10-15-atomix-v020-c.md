# Atomix Round 22 — Plan C (Watch together, Quick Connect, the activity log, stats) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People in different places watch the same film in step; a TV signs in by showing a code; admins see what happened on the server; each profile sees what it watched and listened to.

**Architecture:** Watch together is an in-memory room store (`src/together.js`) with a fake-clock-friendly design: the server keeps the room's position (a position at a time), playing/paused and who's ready; each member's player holds a Server-Sent Events stream for the room's state and posts its actions. Quick Connect (`src/quickconnect.js`) keeps waiting codes in memory; the waiting screen polls with a private poll token and receives a session cookie when someone signed in approves. The activity log (`src/activity.js`, migration 21) is written from the places things happen (sign-in, plays via `Plays` events, app passwords, Watch together, recordings, scans, settings, users/profiles) and pruned after 30 days. Stats are SQL over Plan A's `plays`.

**Tech Stack:** Node ≥ 22.13, `node:sqlite`, `node:crypto`; plain ES-module browser JS (`EventSource`); `node:test`; Playwright devtools.

**Spec:** `docs/superpowers/specs/2026-10-15-atomix-v020-design.md` (sections 4–7; Migrations 21). Builds on Plans A and B.

## Global Constraints

- Watch together: a 6-letter code (letters and digits without 0/O/1/I) and a link `#/together/<code>`; anyone signed in may join; a profile that may not see the title is refused with "This title isn't available on your profile"; up to 8 people; films and episodes only; each member has its own playback session; play/pause/seek by anyone apply to all; a member more than 2 s from the room is seeked; a member buffering after a play/seek pauses the room with "Waiting for <name>…" until all are ready or 10 s pass; the room ends when its last member leaves or after 10 minutes with nobody connected; at the end of a title the room stops and anyone may start the next episode for the room. Out of scope: Live TV and music.
- Quick Connect: sign-in page → **Sign in with a code** → a 6-character code (same alphabet, 30 bits), valid 5 minutes, refreshed; Settings → Profile → **Quick Connect** → type the code → **Approve** names the device from its user agent; the waiting screen signs in as that account and goes to "Who's watching?"; compared in constant time; admin switch in Settings → Server, on by default; approvals logged.
- Activity log: `activity(id, at, type, user_id, profile_id, text, ip)`; Settings → **Activity** (admins only): newest first, filter by type, profile and day, 50 at a time; kept 30 days; no passwords, tokens or provider addresses in it; settings changes record the setting names only.
- Stats: hours watched and listened this week / month / year; top films, shows, artists, songs by plays; a day-of-week × hour grid; admins: Dashboard → **Household** (per profile totals); Kids see only their own.
- No dependencies; older themes pixel-identical (`oldthemes-compare.mjs compare` → "all pages match"); TV-remote friendly; no browser dialogs.

## Review Focus

1. **Two members press pause and play within the same second** — the room ends in one state, both players agree within 2 s, and neither loops sending the other's state back (Task 1 test `last action wins and nobody echoes`, Task 2 UI check).
2. **A member's tab closes without "leave"** — the room drops it when its event stream closes (after 30 s), stops waiting for it, and a room left empty closes after 10 minutes (Task 1 test `a closed stream leaves the room`).
3. **A Kids profile opening a room link for an R16 film** — refused with the sentence, never shown the title (Task 1 test `a profile that may not see the title is refused`).
4. **Somebody typing codes at random into Quick Connect** — after 5 wrong codes from one account, every waiting code is cancelled (the screens show new ones) and the web lockout counts them (Task 3 test `guessing codes cancels them`).
5. **An approved Quick Connect code used twice, or an old poll token** — the second device gets nothing; the poll token is single-use (Task 3 test `a code signs in once`).

### Task 1: Watch together on the server

**Files:**
- Create: `src/together.js`, `src/api/together.js`
- Modify: `src/app.js` (`core.together`, routes)
- Test: `test/together.test.js` (room logic on a fake clock), `test/together-api.test.js` (routes and the event stream)

**Interfaces:**
- Produces: `CODE_ALPHABET = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'` and `makeCode(length = 6)` (also used by Quick Connect); `class Rooms { constructor({ library, now = Date.now, waitMs = 10_000, emptyMs = 10 * 60_000 }); create({ user, profile, viewer, item }) → { room, member }; join(code, { user, profile, viewer }) → { room, member }; act(code, memberId, action, payload) → state; leave(code, memberId); connect(code, memberId, send: (state) => void) → () => void (disconnect); state(code, memberId) → state; reap() }`.
- State sent to members: `{ code, itemId, playing, position, at (server ms the position was true at), serverNow, waitingFor: [names], members: [{ id, name, ready, connected, you }], last: { name, action: 'played'|'paused'|'seeked'|'joined'|'left'|'next'|'ended', at } | null, ended: boolean }`.
- Actions (`POST /api/together/:code/<action>` with `{ member }`): `play { position }`, `pause { position }`, `seek { position }` → the room's position and playing; after `play` or `seek` the room waits for every connected member's `ready` (each member posts `ready` once its player can play from there) and starts when all are ready or `waitMs` passes; `buffering` during playback → pause + wait for that member; `ready`; `ended` → `playing: false, ended: true`; `next { itemId }` (an episode the room's members may see: members that can't are removed with that sentence in their stream) → new title at 0, waiting for all; `leave`.
- Routes (cookie + profile): `POST /api/together { itemId }` → `{ code, member, itemId }`; `POST /api/together/:code/join` → `{ code, member, itemId }`; `GET /api/together/:code/events?member=` → `text/event-stream` (`event: state` with JSON data on every change; `: ping` every 15 s; a closed stream marks the member disconnected; a member disconnected for 30 s is removed); the action routes. Errors (exact): 404 `This Watch together room has ended.`; 403 `This title isn't available on your profile`; 409 `This room is full (8 people).`; 400 `Watch together is for films and episodes.`; 403 `You're not in this room.` (a member id from another account/profile).
- Member ids: random 16 bytes base64url, bound to the profile that joined.
