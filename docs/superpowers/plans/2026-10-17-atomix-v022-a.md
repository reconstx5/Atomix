# Atomix Round 24 — Plan A (Home screen you can arrange; v0.22.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Home's rows follow an arrangement — a household default set by an admin, a per-profile copy once a profile changes anything — with pinned rows and a household list of web apps, edited with a remote.

**Architecture:** `/api/home` keeps building rows as today, but every row now carries a stable `key`; a pure function `applyLayout(rows, layout)` orders and hides them, and pinned rows and the web-apps row are built by new row builders. Arrangements and web apps live in two new tables (migration 24). The editor is one new view used for both the profile and the household.

**Tech Stack:** Node ≥ 22.13 (`node:test`, `node:sqlite`), plain ES-module browser JS, Playwright devtools.

**Spec:** `docs/superpowers/specs/2026-10-17-atomix-v022-design.md` section 1 (and Global constraints, section 5's verification).

## Global Constraints

- No dependencies; no Kodi GPL code.
- Kids profiles never see admin data, and never see a title outside their rules; a pinned row is drawn with the viewer's rules every time.
- Older themes stay pixel-identical: `node devtools/oldthemes-compare.mjs compare` → "all pages match" (Home is in that set: older themes get no new control on Home).
- Web-app addresses are `http://` or `https://` only; their pictures are fetched by the server (sniffed, as artwork) and served from Atomix.
- Copy (exact): "Arrange home"; "Reset to household"; "Add a row"; "Show" / "Hide"; "Remove"; "Moving <row title>. Up and down to move, OK to drop."; "Dropped <row title>."; "Web apps"; "Web app addresses start with https:// or http://."; "That playlist isn't available to this profile." (and "…collection…", "…library…" for those pins).

## Decisions this plan makes (spec silent or loose)

- **Migrations per plan:** Plan A adds migration 24 (`home_layouts`, `web_apps`); Plans B and D add 25 and 26. The spec's "migration 24" is the round's schema; splitting keeps each plan's dev database upgradable without editing a migration in place.
- **Where the editor opens:** Settings → Profile → "Home screen" card ("Arrange home", "Reset to household") in every theme; Orbit's Home also gets an "Arrange home" button after the last row. Settings → Server → "Home screen" card for the household arrangement and the web apps. The spec's "Home's …" becomes Orbit-only because Home is in the older-theme compare set.
- **Saving:** the editor saves after every drop, show/hide, add or remove (PUT, last write wins); no Save button.
- **Group keys:** all "Because you watched" rows share key `picks`; each plugin row is `plugin:<rowKey>`; each library's row is `recent-<libraryId>`.

## Review Focus

1. **A pinned playlist that is later deleted, unshared, or made Kids-invisible** — the row silently disappears for that viewer; the editor shows it as "Not available" with Remove (Task 2 test).
2. **A library added after a profile arranged its Home** — its "Recently added" row appears at its default place, not at the end or hidden (Task 1 test).
3. **A household change after a profile saved its own copy** — the profile's order stands; only rows new to it are inserted (Task 1 test).
4. **A web app with an unreachable or non-picture image address** — saved without a picture (initial-letter tile); the error is not shown to non-admins (Task 3 test).
5. **Moving a row with the remote, then pressing Back mid-move** — the row returns to where it was and nothing is saved (Task 4 check).

### Task 1: Layout store, ordering and the API

**Files:**
- Create: `src/home/layout.js`, `test/home-layout.test.js`, `test/home-api.test.js`
- Modify: `src/db.js` (migration 24), `src/app.js` (construct `HomeLayouts`, put it on core as `core.home`), `src/api/library.js` (`/api/home`: every row gets `key`; layout applied), `src/api/account.js` (profile routes), `src/api/admin.js` (household routes)

**Interfaces:**
- Produces:
  - `DEFAULT_ORDER: string[]` = `['continue', 'continue-listening', 'continue-reading', 'live-now', 'watchlist', 'lists', 'recent-*', 'picks', 'plugin:*', 'web-apps']` (`*` matches every key with that prefix, in the order the rows were built).
  - `applyLayout(rows: {key: string}[], layout: Layout|null) -> rows` — rows in the layout's order, hidden ones removed; a row whose key is not in the layout goes right after the nearest row before it (in `DEFAULT_ORDER` / build order) that the layout does place, or first if none. Pin keys not in `rows` are skipped.
  - `type Layout = { order: { key: string, hidden?: boolean }[], pins: Pin[] }`; `validateLayout(x) -> Layout` throws `HttpError(400)`; limits: 80 entries, 20 pins, keys ≤ 80 chars.
  - `class HomeLayouts { constructor(db); household(): Layout|null; profile(profileId): Layout|null; effective(profileId): { layout: Layout|null, source: 'profile'|'household'|'default' }; saveHousehold(layout); saveProfile(profileId, layout); resetProfile(profileId) }`.
  - Routes: `GET /api/home/layout` → `{ source, layout, rows: [{ key, title, hidden, pin? }] }` (every row this viewer could see, in effective order, including empty and hidden ones); `PUT /api/home/layout` `{ layout }` → saves the profile copy; `DELETE /api/home/layout` → reset; `GET|PUT /api/admin/home-layout` (admin, not Kids; 403 otherwise).
  - Migration 24: `home_layouts(profile_id INTEGER UNIQUE NULL REFERENCES profiles(id) ON DELETE CASCADE, layout TEXT NOT NULL, updated_at INTEGER NOT NULL)` (the household row has `profile_id` NULL — enforce one with a partial unique index); `web_apps(id INTEGER PRIMARY KEY, name TEXT NOT NULL, url TEXT NOT NULL, image TEXT, kids INTEGER NOT NULL DEFAULT 0, position INTEGER NOT NULL DEFAULT 0, created_at INTEGER NOT NULL)`.

- [ ] **Step 1: Failing tests** (`test/home-layout.test.js`, pure; `test/home-api.test.js`, over HTTP with `startAtomix`)
  - `applyLayout orders and hides`: rows `continue, watchlist, recent-1` + layout `[{watchlist}, {continue, hidden}, {recent-1}]` → keys `['watchlist', 'recent-1']`.
  - `a row new to a layout goes to its default place`: layout `[{continue}, {picks}]`, rows `continue, recent-7, picks` → `['continue', 'recent-7', 'picks']`.
  - `household changes don't move a profile's own order`: profile saves `[{lists}, {continue}]`; household later saves `[{continue}, {lists}, {watchlist}]` → profile's `/api/home` keys start `lists, continue`, and `watchlist` follows its default neighbour.
  - `a profile follows the household until it changes something`: `GET /api/home/layout` → `source: 'household'`; after `PUT` → `'profile'`; after `DELETE` → `'household'`.
  - `only admins set the household`: Kids profile and a non-admin account → 403 on `PUT /api/admin/home-layout`; a Kids profile may `PUT /api/home/layout` (its own).
  - `a bad layout is refused before saving`: 81 entries → 400; a key of 81 chars → 400.
  - `/api/home rows carry key`: every row has a string `key`.
  - migrations test: a v23 database upgrades to 24 (tables present).
