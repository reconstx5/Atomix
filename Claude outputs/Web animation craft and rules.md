# Fast, small, interruptible motion wins everywhere

Good web animation in November 2026 comes down to a short set of checkable rules: animate only to show cause, state change or spatial continuity; keep UI motion under about 300ms with an ease-out curve; move only `transform` and `opacity`; make everything interruptible; and animate less the more often an interaction happens, down to nothing for keyboard-driven actions. Design systems and expert practitioners agree closely on the numbers (50-150ms for feedback, 150-300ms for small enters and exits, 300-500ms for full-screen changes), so a reusable skill can encode them as tokens and lint-style checks. The browser platform now covers most of what once needed a library: `linear()` springs, individual transform properties, `@starting-style` entry animations, same-document view transitions and, since October 2026, scroll-driven animations all work across engines, and each degrades to "no animation" when written as progressive enhancement. Accessibility has two hard floors (pause controls for auto-motion over 5 seconds, no flashing above 3 per second) and one practical requirement: under reduced motion, replace movement with a fade; do not delete the feedback. For a Kodi-like media hub the evidence points to a card focus scale of 1.05-1.1 over about 200ms ease-out, paired with a border or colour change that appears on the same frame as the key press. On TV hardware the animation is rarely the bottleneck; layout reads per key press, layer memory and decade-old Chromium builds are, so the hub needs motion tiers (full, reduced, none) with the plain experience as the baseline. Several numbers people commonly quote (Netflix hover scale and delay, spinner delay thresholds on TV, backdrop debounce, trailer autoplay delay) have no retrievable primary source and appear below only as labelled conventions.

## Frequency decides whether anything should animate at all

The first decision is whether to animate, and the sources agree on the test. Vercel's guidelines allow animation only to clarify cause and effect or add deliberate delight ([Vercel](https://vercel.com/design/guidelines)). Emil Kowalski names the valid purposes as explaining how a feature works, indicating a state change, and modal enter/exit, and warns that animating everything dilutes each animation ([Great animations](https://emilkowal.ski/ui/great-animations)). The deciding variable is repetition: **keyboard-initiated actions should not animate**, because they repeat hundreds of times a day and animation makes them feel slow and disconnected ([Great animations](https://emilkowal.ski/ui/great-animations)). NN/g states the same gradient, saying the more often users see an animation the shorter and subtler it should be ([NN/g](https://www.nngroup.com/articles/animation-duration/)), and Apple adds that people must never be made to wait for an animation, especially a repeated one ([Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion.md)).

That yields a usable ladder (a synthesis of those sources, not a quotation from any one). Keyboard-triggered or seen a hundred times a day: no animation. Seen tens of times a day: opacity or colour only, 50-150ms. Occasional surfaces such as modals, drawers and toasts: a standard enter and exit. Rare moments such as onboarding or success: expressive motion is allowed. Carbon formalises the last distinction as "productive" versus "expressive" motion, with expressive used sparingly ([Carbon](https://carbondesignsystem.com/elements/motion/overview/)). This ladder matters doubly for a remote-driven media hub, where almost every interaction is a key press.

Several rules hold regardless of frequency. Errors, confirmations and focus indicators show without delay; Atlassian's focus-state duration token is 0ms, and focus moves and screen-reader announcements fire at the start of an animation, not the end ([Atlassian](https://atlassian.design/foundations/motion/applying-motion)). Motion is never the only carrier of information, and dismissal direction matches entry direction ([Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion.md)). Top-level page navigation uses a quick fade; it does not slide large surfaces ([Fluent 2](https://fluent2.microsoft.design/motion)). Elements with the same role share the same motion ([Carbon: Choreography](https://carbondesignsystem.com/elements/motion/choreography/)).

Disney's twelve principles all have UI analogues, but only at very low amplitude. Easing is "slow in and slow out", hover states are anticipation, staging means one thing moves while the rest stays quiet, and follow-through becomes related elements arriving at slightly different times ([IxDF](https://ixdf.org/literature/article/ui-animation-how-to-apply-disney-s-12-principles-of-animation-to-ui-design)). The concrete UI versions are tiny: press "squash" is `scale(0.97)`, and entrances start from scale 0.9 or higher, never 0 ([7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips)). Carbon contradicts the "arcs" principle outright for productive UI: its motion paths follow the grid and never run diagonally ([Carbon: Choreography](https://carbondesignsystem.com/elements/motion/choreography/)).

## Durations cluster at 100-300ms and ease-out carries the load

### Every design system lands in the same duration bands

NN/g puts most animation at 100-400ms: about 100ms for simple feedback, 200-300ms for substantial changes such as a modal, 400ms only for large movement on big screens, and around 500ms motion starts to feel like a drag. Animations are more often too long than too short ([NN/g](https://www.nngroup.com/articles/animation-duration/)). Emil Kowalski's ceiling for UI is **300ms**; a 180ms select feels more responsive than a 400ms one ([7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips)). Duration scales with distance travelled and area covered ([Material Components Android](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md?ref=androidweekly.io)).

| System | Micro feedback | Small enter/exit | Large or page-level | Longest tokens |
|---|---|---|---|---|
| Material 3 ([source](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md?ref=androidweekly.io)) | Short 50, 100, 150, 200ms | Medium 250, 300, 350, 400ms | Long 450, 500, 550, 600ms | Extra-long 700-1000ms |
| IBM Carbon ([source](https://carbondesignsystem.com/elements/motion/overview/)) | 70ms buttons and toggles, 110ms fades | 150ms small expansion, 240ms toasts and expansion | 400ms large expansion | 700ms background dimming |
| Atlassian ([source](https://atlassian.design/foundations/motion/applying-motion)) | 0ms focus, 50ms list hover, 100ms pressed | 150ms popup enter, 200ms modal exit, 250ms modal enter | 400ms page-level | 600ms onboarding, full-screen overlays |

Material's scale reaches 1000ms because it covers full-screen mobile transitions; for desktop and TV web UI the practitioner ceiling near 300ms is the safer default. Fluent 2 and Apple publish no millisecond values on their motion pages. A consensus default drawn from these tables: hover and press 50-120ms; fades and colour 100-150ms; tooltips and popovers 125-200ms; dropdowns 150-250ms; modals, toasts and drawers 200-300ms in and 150-250ms out; page-level 300-400ms.

Exits run shorter than enters. Atlassian trims 50-100ms (popup 150ms in, 100ms out; flag 250ms in, 200ms out) and NN/g gives 300ms in, 200-250ms out ([Atlassian](https://atlassian.design/foundations/motion/applying-motion); [NN/g](https://www.nngroup.com/articles/animation-duration/)). For loading states, Vercel delays spinners and skeletons by about 150-300ms and then keeps them visible at least 300-500ms to avoid flicker ([Vercel](https://vercel.com/design/guidelines)).

### Three curves cover nearly every case

The rule is: decelerate (ease-out) for anything entering or responding to input, accelerate (ease-in) for things leaving permanently, a standard in-out curve for things that move while staying on screen, and linear only for constant-rate motion such as rotation ([Fluent 2](https://fluent2.microsoft.design/motion); [Smashing/Val Head](https://smashingmagazine.com/2019/02/animation-design-system/)). Ease-out works for entrances because it starts fast, so the UI appears to respond at once, then settles; two dropdowns at the same 300ms differ visibly, and the ease-in one feels slower ([7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips)). The built-in CSS keywords are too weak, so use custom curves ([7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips)).

| Role | Material 3 | Carbon productive | Carbon expressive |
|---|---|---|---|
| On-screen move (standard) | `cubic-bezier(0.2, 0, 0, 1)` | `cubic-bezier(0.2, 0, 0.38, 0.9)` | `cubic-bezier(0.4, 0.14, 0.3, 1)` |
| Enter (decelerate) | `cubic-bezier(0, 0, 0, 1)`; emphasized `cubic-bezier(0.05, 0.7, 0.1, 1)` | `cubic-bezier(0, 0, 0.38, 0.9)` | `cubic-bezier(0, 0, 0.3, 1)` |
| Exit (accelerate) | `cubic-bezier(0.3, 0, 1, 1)`; emphasized `cubic-bezier(0.3, 0, 0.8, 0.15)` | `cubic-bezier(0.2, 0, 1, 0.9)` | `cubic-bezier(0.4, 0.14, 1, 1)` |

Values from [Material Components Android](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md?ref=androidweekly.io) and [Carbon](https://carbondesignsystem.com/elements/motion/overview/). Carbon adds a useful nuance: an element that stays nearby and can be recalled, such as a side panel, uses the standard curve, not the exit curve.

The experts disagree on exits. Emil Kowalski recommends ease-out for both entering and exiting; Material, Carbon, Atlassian and Val Head prescribe ease-in for exits; NN/g notes ease-in suits exits but risks feeling unresponsive when the start is slow. The disagreement dissolves at speed: at 100-200ms either curve reads fine, and ease-in only hurts when the exit is slow. For user-triggered dismissals that must feel instant, a fast ease-out is the safer pick.

### Springs belong to gestures and spatial moves

Material 3 now ships spring tokens as damping ratio and stiffness: 0.9/1400 for small components, 0.9/700 for partial-screen surfaces, 0.9/300 for full-screen moves. Its "effects" springs for colour and opacity are critically damped (ratio 1), so **opacity and colour never overshoot** ([Material Components Android](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md?ref=androidweekly.io)). In CSS, real springs need `linear()`, because `cubic-bezier` can overshoot once but cannot oscillate. Josh Comeau's findings: about 11 points looks robotic, springs need 40 or more, long value lists cost nothing at runtime, and three large springs add about 1.3kB gzipped. Generate them with a tool, store them as custom properties, and provide a `cubic-bezier` fallback overridden inside `@supports (animation-timing-function: linear(0, 1))` ([Josh Comeau](https://joshwcomeau.com/animation/linear-timing-function)). The Linear Easing Generator by Jake Archibald and Adam Argyle does the conversion ([Chrome](https://developer.chrome.com/docs/css-ui/css-linear-easing-function)).

CSS springs have one real limit. On interruption CSS shortens the remaining duration, so a 1600ms spring can replay in 400ms and feel like hitting a wall, while JS spring libraries carry velocity through ([Josh Comeau](https://joshwcomeau.com/animation/linear-timing-function)). Use CSS transitions for predetermined motion and reserve true springs for gesture-driven, interruptible motion. Typical web spring parameters attributed to Emil Kowalski's skills repository (duration 0.3-0.6s with bounce 0 by default, 0.1-0.3 for gesture UIs) come only from a third-party summary and are lower confidence ([Instagit summary](https://instagit.com/emilkowalski/skills/how-to-configure-spring-animations-effectively/)).

## Expert craft reduces to a dozen checkable rules

The practitioner consensus is concrete enough to lint. Emil Kowalski's seven tips: `scale(0.97)` on `:active` so the UI feels like it is listening; never animate from `scale(0)` (his example starts at 0.93 with opacity); skip delay and animation on subsequent tooltips once one is open; ease-out with custom curves; origin-aware `transform-origin`; stay under 300ms; and when a crossfade still looks wrong, bridge the two states with a little `filter: blur()` (2px in his example). His tooltip recipe is `transform 125ms ease-out, opacity 125ms ease-out` from `opacity: 0; scale(0.97)`, anchored to the trigger ([7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips)).

Vercel's guidelines supply the implementation rules: CSS first, then the Web Animations API, then JS libraries; **never `transition: all`**, list properties explicitly; animate `transform` and `opacity`, not `width`, `height`, `top` or `left`; user input cancels in-progress animation; for SVG, transform a `<g>` wrapper with `transform-box: fill-box; transform-origin: center` ([Vercel](https://vercel.com/design/guidelines)). Atlassian caps complexity at one or two properties per transition ([Atlassian](https://atlassian.design/foundations/motion/applying-motion)).

Interruptibility deserves emphasis because it drives a technical choice. The test is to open something and immediately press Escape; the result must be smooth. CSS transitions retarget from the current value, keyframe animations jump, so state changes should be transitions ([Great animations](https://emilkowal.ski/ui/great-animations)). Kodi's skinning engine encodes the same idea: its animations default to `reversible="true"`, reversing from where they are ([Kodi wiki](https://kodi.wiki/view/Animating_your_skin)).

Choreography has firm numbers too. Carbon staggers list entrances by **20ms** per item and caps the whole sequence at **500ms**, which in practice covers roughly a dozen items, so stagger the first screenful and reveal the rest together. Its page-load order runs static shell, static body, dynamic content, primary action, then animated content ([Carbon: Choreography](https://carbondesignsystem.com/elements/motion/choreography/)). Fluent says to skip stagger for very large groups ([Fluent 2](https://fluent2.microsoft.design/motion)). Large or full-screen transitions should carry a continuous element that guides the eye ([Carbon](https://carbondesignsystem.com/elements/motion/overview/)).

Cheap-feeling motion is almost always too slow, too large, too frequent or wrongly eased. The named anti-patterns: ease-in or linear on entrances; scaling from 0 or from the centre when a trigger exists; blocking, non-cancellable animation; layout-property animation; keyframes where a transition was needed; tooltips that re-delay while the user scans a toolbar; spinner flicker; bezier overshoot faking a spring; and no reduced-motion path ([NN/g](https://www.nngroup.com/articles/animation-duration/); [7 practical animation tips](https://emilkowal.ski/ui/7-practical-animation-tips); [Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion.md); [Josh Comeau](https://joshwcomeau.com/animation/linear-timing-function)). The recognisable "AI-generated" signature (uniform 300-500ms ease-in-out, fade-up on every section with 20-40px travel, long staggers, hover scale of 1.05 or more on every card) follows directly from breaking these rules, though no source names that pattern; it is an inference. The fix order is to cut duration, cut distance and scale delta, switch to ease-out, fix the transform origin, then consider deleting the animation. Emil also advises reviewing animations the next day with fresh eyes ([Great animations](https://emilkowal.ski/ui/great-animations)).

One widely repeated rule, gating hover effects behind `@media (hover: hover) and (pointer: fine)`, did not appear in any source read for this research. It is sound practice for a hub used by touch and remote, but it is unverified as an attributed rule.

## The platform now does natively what libraries used to

### Compositor properties first, layers sparingly

The render pipeline runs style, layout, paint, composite, and triggering one stage triggers every later one. Motion's tier list ranks compositor-thread animation of `transform`, `opacity`, `filter` and `clip-path` through CSS or WAAPI at the top; the same properties driven from the main thread next; FLIP after that; paint-triggering properties (`background-color`, `border-radius`, gradients, CSS variables) lower; layout-triggering properties (`width`, `margin`, `top`) near the bottom; and layout thrashing last ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). Google's guide is stricter and names only `transform` and `opacity` ([web.dev](https://web.dev/articles/animations-guide)). Whether `background-color` animates on the compositor in current Chrome is unconfirmed; verify per case in DevTools.

Layer promotion has a cost. `will-change` forces a layer, should not be applied early or broadly, and belongs in static CSS only for elements that are always about to change ([web.dev](https://web.dev/articles/animations-guide)). Blur cost grows with radius and layer size; Framer flags blur above 10px ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). Changing a CSS custom property always triggers paint, and an inherited global variable can force style recalculation across a whole tree (one cited site: over 1,300 elements, about 8ms per frame); scope variables close to use or register them with `@property { inherits: false }` ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). Two standard techniques follow, offered here as established practice, not as sourced findings: animate the opacity of a pre-painted shadow on a pseudo-element in place of `box-shadow`, and reveal with `clip-path: inset()` or `scale` in place of `height`.

### Transitions, keyframes and WAAPI each have a job

Use transitions for state A to state B, keyframes for loops and on-load sequences, and `element.animate()` when values are computed at runtime. All three run on the compositor for eligible properties, whereas requestAnimationFrame-driven libraries such as GSAP run on the main thread ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). Emil Kowalski cites a Vercel shared-layout animation that dropped frames during page load until it moved to CSS ([Great animations](https://emilkowal.ski/ui/great-animations)). To persist a WAAPI result, MDN's pattern is `fill: "forwards"`, await `finished`, `commitStyles()`, then `cancel()`; the simpler route is to set the final style as the real style and animate to it ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Animation/commitStyles)).

Entry animations from `display: none` are now cross-browser: put the start values in `@starting-style` and add `allow-discrete` to the `display` transition, inside the `transition` shorthand, since a standalone `transition-behavior` declared earlier is reset by the shorthand ([web.dev](https://web.dev/blog/baseline-entry-animations)). Smooth top-layer exits and `height: auto` animation remain Chromium-only, but both are harmless to ship because other browsers simply snap; `interpolate-size: allow-keywords` is inherited, so one declaration on `:root` suffices ([MDN](https://developer.mozilla.org/docs/Web/CSS/Reference/Properties/interpolate-size)).

View transitions need the most care. The page is **frozen while the update callback is pending**, so fetch data before calling `startViewTransition()`; only one document transition runs at a time and a new one makes the previous skip to its end; the default group animation of width and height runs layout every frame ([Chrome](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). A `view-transition-name` may appear on at most one element before and one after, and duplicates cause the DOM update to apply with no transition. For lists, use `match-element`, or assign a fixed hero name to the clicked thumbnail just before the transition and clear it after `finished` ([Chrome modern web guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-behaviors/same-document-transitions)). The API does not manage focus; move it explicitly after the update. Direction-aware navigation uses `types` such as `['forwards']` styled with `:active-view-transition-type()`, though view-transition types were not in Firefox's initial implementation, so toggling a class on `<html>` is the portable route ([Chrome](https://developer.chrome.com/docs/web-platform/view-transitions/same-document); [Chrome 2025 update](https://developer.chrome.com/blog/view-transitions-in-2025)). Cross-document transitions carry a hard 4-second timeout from navigation start and fail silently on slow servers ([CSS-Tricks](https://css-tricks.com/cross-document-view-transitions-part-1/)).

For reordering and shared elements, FLIP (measure first and last positions, invert with a transform, play) remains the hand-rolled option and rates just below pure compositor animation ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). Choose a view transition when the change is discrete and brief (sort, filter, route) and FLIP through WAAPI when the user can trigger changes rapidly, since view transitions skip or snap on interruption. Scroll-linked effects should use `animation-timeline` behind `@supports`; JS that reads `scrollTop` lags native scroll ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)). IntersectionObserver remains the cross-browser tool for "play once when visible" and for pausing off-screen loops.

### Verify in DevTools, and a library is rarely needed

Record in the Performance panel and check that rendering work is absent during the animation; turn on Paint Flashing, where a properly accelerated animation shows no green ([web.dev](https://web.dev/articles/animations-guide); [Chrome](https://developer.chrome.com/blog/hardware-accelerated-animations)). Batch layout reads before writes; interleaving them is the worst performance tier ([Motion](https://motion.dev/blog/web-animation-performance-tier-list)).

For a no-build project, native features cover hover and press states, enter and exit, accordions, scroll reveals, page transitions and list reorder. A library earns its place for velocity-preserving springs, drag with inertia, long scrubbable timelines or SVG morphing. Vendor-published sizes put Motion's mini `animate` at about 3.1kB (4.7kB with springs) against GSAP's 27.3kB core ([Motion](https://motion.dev/docs/gsap-vs-motion)). GSAP has been free, including former Club plugins, since spring 2025 ([Webflow](https://webflow.com/blog/gsap-becomes-free)), but Motion's page describes it as closed source under a Webflow-controlled licence. That is a competitor's characterisation and the licence text itself was not read; for a redistributable self-hosted project, MIT-licensed Motion carries less risk.

## Reduced motion means substitute a fade; focus never waits

### Two Level A floors and one near-mandatory AAA criterion

WCAG 2.2.2 (Level A) requires a pause, stop or hide mechanism for any moving content that starts automatically, lasts more than **5 seconds** and appears alongside other content. One decorative loop can fail a whole page, and pausing only while focused does not count ([W3C 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide)). WCAG 2.3.1 (Level A) forbids more than **3 flashes in any one second** above the size and luminance thresholds ([W3C 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold)). WCAG 2.3.3 (AAA) says interaction-triggered motion can be disabled unless essential, and `prefers-reduced-motion` is its sufficient technique. Its definition of "motion animation" excludes colour and opacity changes, which is the standards basis for substituting a crossfade; blur was removed from that exclusion by erratum, so blur-in effects should be reduced too ([W3C 2.3.3](https://w3.org/WAI/WCAG21/Understanding/animation-from-interactions)). The 2.2.2 text never cites the media query, so honouring the OS preference does not obviously satisfy it; a background loop or auto-rotating hero still needs a visible control. WCAG 3 remains a Working Draft (3 March 2026) whose motion requirements are at "developing" status ([W3C WCAG 3 draft](https://www.w3.org/TR/2026/WD-wcag-3.0-20260303/)).

The risk model is qualitative but consistent. Val Head identifies three factors: how much of the screen moves, mismatch between motion and the user's own input (parallax, scroll-jacking), and perceived distance covered ([A List Apart](https://alistapart.com/article/designing-safer-web-animation-for-motion-sensitivity)). WebKit lists scaling and zooming, spinning, multi-speed movement, plane-shifting and peripheral motion as triggers ([WebKit](https://webkit.org/blog/7551/responsive-design-for-motion/)). Colour fades, opacity changes and small scale changes are likely safe ([Smashing/Val Head 2020](https://www.smashingmagazine.com/2020/09/design-reduced-motion-sensitivities)). No source gives numeric thresholds, so any pixel limit in a skill is a house heuristic. The same 20px slide is harmless on a tooltip and risky on a whole page.

### Reduce, don't remove, and handle JS separately

The preference means "reduce", not "none". WebKit says to remove only known vestibular triggers and substitute a simpler animation where motion carries meaning ([WebKit](https://webkit.org/blog/7551/responsive-design-for-motion/)); Val Head's workable substitution swaps transform for opacity while keeping duration, easing and delays ([Smashing/Val Head 2020](https://www.smashingmagazine.com/2020/09/design-reduced-motion-sensitivities)). The blanket `*` reset is criticised as a sole strategy: it strips helpful motion and does not govern JavaScript animation, where it can produce motion that is "super fast and dizzying" ([CSS-Tricks](https://css-tricks.com/?p=363057)). Two structures are preferred: Tatiana Mac's no-motion-first approach, with static styles as the default and animation added inside `@media (prefers-reduced-motion: no-preference)` ([Tatiana Mac](https://www.tatianamac.com/posts/prefers-reduced-motion)), or duration tokens as custom properties that one media query retunes ([CSS-Tricks, Eric Bailey](https://css-tricks.com/?p=286790)).

Specific cases follow from that. Smooth scrolling is opt-in under `no-preference`, and video does not autoplay for reduced-motion users ([Smashing](https://www.smashingmagazine.com/2021/10/respecting-users-motion-preferences/)). For view transitions, Chrome's documentation says a reduced-motion preference does not mean no motion and suggests a subtler animation; keeping the crossfade while dropping the positional morph fits that ([Chrome](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)). WAAPI ignores CSS media queries, so JS must branch on `matchMedia('(prefers-reduced-motion: reduce)')` and listen for changes ([WebKit](https://webkit.org/blog/7551/responsive-design-for-motion/)).

An in-app motion setting is worth building. Many people do not know the OS setting exists; the toggle should default to the OS preference and persist the choice ([Smashing/Val Head 2020](https://www.smashingmagazine.com/2020/09/design-reduced-motion-sensitivities)). Netflix's TV app sets the precedent with a per-profile "Reduce animation effects when navigating on TV" setting ([What's on Netflix](https://whats-on-netflix.com/news/netflix-introduces-new-animations-in-tv-app-how-to-turn-them-off)). Styling from a `data-motion` attribute on the root, seeded by the media query, lets one mechanism serve the OS preference, the user setting and device capability tiers.

### Focus indication is instant and persistent

WCAG 2.4.7 requires a visible focus indicator that is not time limited, 2.4.11 requires that the focused component is not entirely hidden by author content (use `scroll-padding` against sticky bars), and 2.4.13 (AAA) asks for a 2 CSS pixel perimeter at 3:1 contrast ([W3C 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible); [W3C 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum); [W3C 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance)). No standard explicitly bans animating a focus ring; the "instant focus" rule is an inference from the persistence requirement, Atlassian's 0ms focus token and a published lint rule against transitioned focus rings ([React Doctor](https://www.react.doctor/docs/rules/react-doctor/no-transitioned-focus-ring)). The conservative rules: no transition on `outline` for the arrival of focus; use `outline`, which survives forced-colours mode, over `box-shadow` alone; never queue or block key input behind an in-flight animation.

Screen-reader timing is separate from animation timing. A live region must exist in the DOM before content is injected ([Sara Soueidan](https://sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/)), toasts must not steal focus, and auto-dismissing toasts conflict with 2.2.1 ([Adrian Roselli](https://adrianroselli.com/2020/01/defining-toast-messages.html)). Auto-rotating carousels stop on keyboard focus and need a stop button first in their tab order ([W3C APG](https://w3c.github.io/wai-website/ARIA/apg/patterns/carousel/)). The related authoring rule is "visible at rest": the base style is the final readable state, and hidden start states live only inside keyframes or behind a class that JS sets once it knows it will animate.

For testing, Chrome DevTools' Rendering tab emulates `prefers-reduced-motion`, `prefers-contrast`, `prefers-reduced-transparency` and `forced-colors` ([Chrome DevTools](https://developer.chrome.com/docs/devtools/rendering/emulate-css)); Firefox uses the `ui.prefersReducedMotion` pref in `about:config` ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)); Playwright takes `reducedMotion: 'reduce'` ([Playwright](https://playwright.dev/docs/emulation)).

## A media hub needs a 200ms focus scale and a fallback tier

### Cards: scale 1.05-1.1, never scale alone

Published focus scales cluster tightly, and every platform pairs scale with a second, non-motion cue.

| Source | Focus scale | Timing | Second cue |
|---|---|---|---|
| Android TV design guide ([source](https://developer.android.com/design/ui/tv/guides/styles/focus-system)) | 1.025, 1.05, 1.1 by element size (bigger element, smaller factor) | none published | outline, glow (2-32dp), colour |
| Compose for TV cards ([source](https://composables.com/jetpack-compose/androidx.tv/tv-material/objects/CardDefaults/api.md)) | 1.1 focused; pressed returns to 1.0 | none exposed | 3dp border |
| Android Leanback ([source](https://android.googlesource.com/platform/frameworks/support/+/refs/heads/androidx-main/leanback/leanback/src/main/res/values/dimens.xml?format=TEXT)) | 1.06, 1.10, 1.14, 1.18 | selects 150ms, row moves 250ms | n/a |
| Jellyfin web ([source](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/components/cardbuilder/card.scss)) | 1.07 on an inner box | `transform 200ms ease-out` | no-animation mode with a reserved transparent border |
| Kodi skin engine examples ([source](https://kodi.wiki/view/Animating_your_skin)) | zoom to 120% in examples | 200ms, easing "out", reversible | n/a |
| Apple tvOS ([source](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection.md)) | larger, no number published | "instant" feedback | deeper shadow, parallax |

**About 200ms ease-out** is the best-supported single value for focus scale on the web, and nothing found supports focus animations longer than 250ms. Jellyfin, the closest open-source analogue (a plain-CSS web UI used on TVs), supplies three implementation details worth copying: it scales an inner element, not the card itself; it forces the focused card to `position: relative; z-index: 10` so it paints over neighbours; and it gates all animation behind a class, with a fallback mode that reserves a transparent border so a coloured border can appear with no layout shift ([Jellyfin card.scss](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/components/cardbuilder/card.scss)). Its hover overlay fades in over 0.2s on both `:hover` and `:focus-within`. Reserve padding in horizontally scrolling rows so the scaled card is not clipped, and set the transform origin toward the inside for first and last cards; those two points are engineering inference.

The press state dips back: Compose's pressed scale returns to 1.0 and tvOS's highlighted state returns to unfocused size, so Enter or click should pull the focused card toward 1.0. Netflix's web row effect used only `transform` and `opacity`, pushed neighbours aside with JS-set `translate3d()` and authored images at 2x resting size to stay sharp ([Wealthfront Engineering](https://eng.wealthfront.com/2015/06/30/implementing-netflix-redesign/)). That neighbour displacement is the expensive variant; simple overlap suits a no-build app. No credible published values exist for Netflix's hover scale or hover-intent delay, so none are given here.

### Remote use: feedback inside 100ms, held keys are a different mode

No platform publishes a millisecond budget for focus feedback. The rule is qualitative and strict: Roku says animations must never throttle the pace of interaction ([Roku](https://developer.roku.com/dev/docs/key-design-principles.md)), and BBC guidance says not to rely on animation because some certified devices cannot animate smoothly ([BBC GEL mirror](https://bbcbreakingnews.pages.dev/gel/features/how-to-design-for-interactive-tv-experiences)). The hard numbers come from general HCI, where **0.1 second** is the limit for feeling instantaneous ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)), and from Disney+ Hotstar's work on Tizen and webOS, which cut tray interaction latency from about 400ms to about 100ms and saw weekly card views per user rise from 111 to 226 ([web.dev](https://web.developers.google.cn/case-studies/hotstar-inp?hl=en)). The practical design: the border or colour change paints on the first frame after keydown, and the 200ms scale tween starts on that frame as an interruptible enhancement.

A held arrow key needs different treatment from a single press. Norigin's spatial navigation docs use throttle values of 100-150ms between moves as examples, noting that an unthrottled held key moves focus dozens of times per second, and recommend `focus({ preventScroll: true })` so browser auto-scroll does not fight custom scroll logic ([Norigin](https://devportal.noriginmedia.com/docs/Norigin-Spatial-Navigation/guides/performance)). An LG/Enact engineer reports that native scrolling reached 60fps on low-end webOS where per-frame JS translation could not, calling `scrollTo()` with **`behavior: smooth` for single presses and `instant` for held keys** ([GitNation](https://gitnation.com/contents/overcoming-performance-limitations-in-react-components-for-embedded-devices)). Hotstar's alternative transforms the row track with dimensions read once per row, and makes follow-up work cancellable so moving on aborts the previous card's trailer fetch ([web.dev](https://web.developers.google.cn/case-studies/hotstar-inp?hl=en)). Both avoid per-frame JS and per-card measurement, which is the real cost: Hotstar's original jank came from a library re-reading about 70 focusable positions on every key press. For a plain CSS and Preact app, native scroll is simpler and degrades better. Detecting the held state through `event.repeat` and deferring backdrop and metadata updates until focus rests is a reasonable implementation, though it is inference.

Amazon adds three points for web apps on TV: set initial focus on an actionable element at launch, apply style changes in the next `requestAnimationFrame`, and avoid heavy CSS animation during video playback because both compete for the GPU ([Amazon Vega](https://developer.amazon.com/docs/vega/0.22/webview-app-performance-best-practices.html)). ITV keeps a "focus memory" keyed by item ID so returning to a screen restores the previously focused item ([ITV Technology](https://medium.com/itv-technology/how-were-optimising-the-performance-on-the-itv-hub-by-windowing-our-content-bbb1df4a4b69)). Restoring focus and scroll position on Back matters more to a remote user than any transition.

### Moving between screens, loading and the player

Screen changes should default to a fast fade, with view transitions layered on where supported. Roku recommends carrying a relevant element from one screen to the next for continuity while keeping animation minimal ([Roku](https://developer.roku.com/dev/docs/key-design-principles.md)), and the poster-to-hero morph is exactly what a shared `view-transition-name` provides. Because the page freezes during the update and only one transition runs at a time, skip the transition when navigation comes from a repeating key or another transition is active. Kodi itself runs no close animation when switching to fullscreen video; entering playback is immediate ([Kodi wiki](https://kodi.wiki/view/Animating_your_skin)). By analogy with Leanback's 250ms row transitions, 200-300ms is a sensible page-level duration, an inference rather than a published figure.

Loading follows NN/g's thresholds: under about **1 second show no loader at all** because the flash is jarring; skeletons for full-view loads under about 10 seconds; a spinner only for a single module in the 2-10 second band; a progress bar beyond 10 seconds ([NN/g](https://www.nngroup.com/articles/skeleton-screens/)). Samsung advises calling `img.decode()` before display, serving images at display size and avoiding animated GIFs ([Samsung](https://developer.samsung.com/smarttv/develop/guides/web-app-memory-optimization-guide.html)). A single opacity fade over a flat or dominant-colour placeholder is the cheapest acceptable poster reveal. A shimmer is a looping large-area animation, so static skeletons are the right default on TV and under reduced motion; one vendor write-up recommends removing animated loaders entirely on low-end Tizen ([Oxagile](https://www.oxagile.com/article/samsung-tizen-tv-apps-for-all-tips-for-low-end-tvs/)).

Player guidance is thin. The only concrete published number is from Video.js: controls hide after **2 seconds** of inactivity, with activity polled every 250ms to avoid per-mousemove work, and that comes from a 2013 post ([Video.js](https://legacy.videojs.org/blog/hiding-and-showing-video-player-controls)). BBC guidance puts controls and onward prompts in the lower third and hides the interface soon after playback starts ([BBC GEL mirror](https://bbcbreakingnews.pages.dev/gel/features/how-to-design-for-interactive-tv-experiences)). Norigin suggests throttling keys to 300ms during scrubbing ([Norigin](https://devportal.noriginmedia.com/docs/Norigin-Spatial-Navigation/guides/performance)). Reasonable defaults beyond that (fade controls in over 100-150ms and out over 250-400ms; never hide while paused or while a control is focused; update the scrubber on the same frame and debounce the actual seek) are inference. No published values were found for skip-intro windows, next-episode countdowns or other players' auto-hide timing.

Hero and backdrop motion is likewise mostly cautionary. Titan OS says to replace auto-playing hero trailers with static images on low-end models and to drop `backdrop-filter` and heavy shadows during carousel navigation ([Titan OS](https://docs.titanos.tv/performance-optimization-strategies.md)). Debouncing a backdrop crossfade until focus rests (around 150-400ms, by analogy with Leanback's 150ms header delay) and crossfading exactly two stacked layers is an engineering inference; no source publishes a backdrop debounce, a trailer autoplay delay or Ken Burns parameters. A Ken Burns drift is continuous full-screen zoom, so it must be off under reduced motion and needs a pause control under 2.2.2 if it runs beyond 5 seconds.

### TV hardware sets the ceiling

Samsung's numbers frame the budget: about 16ms per frame, and each compositing layer costs width times height times 4 bytes, so a full-screen 1080p layer is about **8MB** and a decoded 4K image about 33MB. Its rules: do not put `translateZ(0)` on every card, enable `will-change` only during the animation, avoid stacking full-screen layers, and virtualise lists over about 100 items ([Samsung](https://developer.samsung.com/smarttv/develop/guides/web-app-memory-optimization-guide.html)). Jellyfin's permanent `will-change: transform` on every card contradicts this; promote only the focused card. Hotstar measured the same page rendering in 1.39 seconds on a 6x-throttled laptop and **6.47 seconds on a real TV**, and found a 2020 LG TV running Chrome 68 ([web.dev](https://web.developers.google.cn/case-studies/hotstar-inp?hl=en)). A low-end Fire TV Stick has about 1GB RAM and throttles thermally in long sessions ([Amazon](https://developer.amazon.com/apps-and-games/blogs/2026/07/blueprint-series-pt3-performance)).

Old Chromium means view transitions, `linear()`, `@starting-style` and scroll timelines will not exist on many in-service TVs, so the fallback is the primary TV experience, not an edge case. The practical outcome, implied by BBC's "non-anim devices", Netflix's setting, Titan OS's low-tier fallbacks and Jellyfin's animation gate, is three motion tiers on one root attribute: **full** (scale, glow, backdrop crossfade, view transitions), **reduced** (border or small scale, opacity fades, no blur, static hero) and **none** (instant border and colour focus only). Select by OS preference, user setting and device capability.

A starting token set for the hub, synthesised from the values above and offered as a recommendation, not a sourced standard:

```css
:root {
  --dur-instant: 0ms;      /* focus ring, errors */
  --dur-fast: 100ms;       /* press, hover colour */
  --dur-base: 200ms;       /* card focus scale, popover enter, overlays */
  --dur-slow: 300ms;       /* modal, screen change */
  --ease-out: cubic-bezier(0.05, 0.7, 0.1, 1);   /* Material emphasized decelerate */
  --ease-in: cubic-bezier(0.3, 0, 1, 1);         /* Material accelerate */
  --ease-move: cubic-bezier(0.2, 0, 0, 1);       /* Material standard */
  --focus-scale: 1.07;     /* posters; ~1.04 wide cards; none for hero tiles */
  --press-scale: 0.97;
}
:root[data-motion="reduce"] { --focus-scale: 1; --dur-base: 150ms; --dur-slow: 150ms; }
:root[data-motion="none"]   { --focus-scale: 1; --dur-fast: 0ms; --dur-base: 0ms; --dur-slow: 0ms; }
```

## Conclusion

The research changes the shape of the problem. Motion craft is less a matter of taste than expected: independent design systems converge on the same duration bands and easing roles, and the practitioner rules are mechanical enough that a skill can run them as checks (`transition: all`, `scale(0)`, ease-in on entrances, durations over 300ms on controls, layout-property animation, transitioned focus rings, a hidden base state, a missing reduced-motion path). The interesting judgement sits one level up, in deciding that a remote-driven interface should animate far less than a pointer-driven one, because nearly everything in it is a high-frequency keyboard action.

For the media hub, the highest-value work is structural, not decorative: one root attribute that carries motion tier, instant non-motion focus cues with scale as enhancement, transitions over keyframes so focus changes retarget, measurement-free key handling, and focus and scroll restoration on Back. The evidence has gaps exactly where media apps are most distinctive. Backdrop debounce, trailer delay, player auto-hide and hover-intent timings have no published values, and laptop throttling under-predicts TV slowness by a factor of four to five, so those numbers have to be tuned on a real television. The best next primary sources are Jellyfin's backdrop code and the Estuary skin's XML, neither of which was inspected here.
